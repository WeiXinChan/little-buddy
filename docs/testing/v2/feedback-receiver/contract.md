# Self-hosted device feedback receiver

This is the reversible implementation candidate for an existing-backend receiver while the receiving platform/maintainer decision remains unspecified. It does not activate a service, appoint a human responder, submit a real issue or enable the Android provider. It adds no external platform, account system, dependency, notification or cloud inference.

## Real startup and transport

`backend.v2.live` accepts optional `--feedback-database /private/state/issues.sqlite` and `--feedback-copies-policy single-store-no-exports-v1`. Omitting the database leaves the endpoint disabled. Preflight validates a private operator/service-owned parent and existing database file without creating a database. Actual serving creates/opens SQLite mode 0600 under the private directory, starts expiry maintenance, and exposes `/v2/feedback` on the existing loopback TLS listener. Existing device Bearer authentication and expiry apply. Device scope comes from the authenticated token's SHA256, never a caller-supplied device/parent boolean. The voice route keeps its 16000-byte decoder limit even when the listener permits bounded larger issue messages. Voice and feedback have separate concurrency slots.

A client opens a separate authenticated WSS connection and waits for `{"v":1,"type":"feedback_ready","protocol":"feedback-v1"}`. Each request is one JSON text message, at most 400000 UTF-8 bytes. Canonical UUIDv4 `request` correlates the reply; canonical UUIDv7 `id` is the original persistent idempotency/deletion key. Its immutable leading 48-bit epoch-millisecond timestamp bounds first admission to one hour (up to two minutes future clock skew). Existing admitted retries retain their original receipt; UUIDv4 is supported only for legacy read/withdraw, not new admission. See [RFC 9562 §5.7](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7). Operations:

- Submit: `{"v":1,"request":"UUID","operation":"submit","id":"UUID","category":"IMAGE","description":"adult report","logs":"BASE64"}`. Category is one of the existing six Android enums. Description is 1–2000 Unicode code points. Empty logs are allowed. Nonempty logs are at most 256KiB / 1000 ASCII numeric/enum lines in the existing FeedbackCore format; unknown/free-text/transcript fields are rejected.
- Read: `{"v":1,"request":"UUID","operation":"read","id":"UUID"}`. Returns only that device's row: id, submitted, delete_by, state, category, description, logs (base64), reply. All times are epoch milliseconds. Unknown IDs return `missing` and do not reveal another device's record.
- Withdraw: same envelope with `operation:"withdraw"`. Atomically removes the canonical store's description/logs/reply/digest, marks a content-free tombstone, and prevents late upload or operator processing. Returns received_at, delete_by and all_copies_deleted. Repeat withdrawal is safe. Withdraw-before-submit creates a durable tombstone. Acknowledgements are issued only after the SQLite transaction commits.

Replies are `{"v":1,"request":"UUID","ok":true,"result":{...}}` or finite error codes invalid/storage/clock/expired/deleted/conflict/capacity/missing. No admin operation exists on this route. Duplicate fields, unexpected fields, malformed base64, binary/oversized messages and caller-invented metadata do not create issues. A connection accepts at most 128 requests; only one feedback connection is admitted at once.

## Retention and maintenance

The original server submission time fixes the seven-day deadline. Reads, retries, processing and replies never extend it. Retried payloads must exactly match their original digest; a different body under the same key is a conflict. Withdraw immediately clears canonical content and stops maintainer access, earlier than the 24-hour maximum. Tombstones retain only necessary routing/status/time fields until the original deadline; an unknown fresh-key tombstone lasts only until the key's original first-admission window ends. An expired/legacy inadmissible unknown key needs no retained tombstone. Once original issue/tombstone rows expire, replay of that same old UUIDv7 is still rejected by its immutable timestamp; no permanent identifier registry is needed. Every access sweeps expiry and the active runtime schedules cleanup at the next deadline with at most 60-second idle polls. Restart sweeps before access; a failed expiry task disables the receiver and closes its active connection. Clock rollback blocks reads/new submissions/replies while still permitting immediate redaction. This is not a claim of globally trusted wall time or deletion while the host is powered off.

SQLite uses secure_delete, FULL synchronization, private temporary storage and DELETE journaling. This implementation creates no material exports, backup jobs or secondary indexes. `store_deleted` proves deletion only in this canonical store. The wire maps it to all_copies_deleted only when the operator explicitly reviewed the single-store/no-exports policy. Without that decision, the client must remain in deleting, not display deleted. External backups, operator-created copies and OS/storage forensic guarantees are not proven by a database transaction; do not enable the copy-policy declaration without reviewing the actual deployment.

Local OS-authorized maintenance is `python -m backend.v2.feedback_admin --database /private/state/issues.sqlite list|show|processing|reply|sweep`. `list` prints routing/status metadata only. `show --device HASH --id UUID` is an explicit confidential material view, not a logging command; do not redirect materials to retained terminal logs/files or create untracked copies. `reply` reads a non-echoed interactive value through getpass, without creating a material staging file or shell-history reply argument. Operators must remove any operator-created controlled material view within the issue's original deadline and immediately on withdrawal. No fixed human response SLA is implied.

## Remaining client and operational work

Android still needs the reviewed FeedbackProvider transport, grant-at-admission gating, persistent original-key withdrawal, status/reply refresh and actual factory injection. Its SSH client currently permits only `/v2/voice`; add only the exact feedback route and preserve CA/host-key verification. Concurrent voice/feedback attempts need isolated tunnel forwarding (the existing fixed local port cannot be bound twice). No arbitrary URL/redirect/credential export or server-issued parent Grant is introduced. Final operator/platform responsibility, actual deployment copy inventory and integrated device tests remain pending.

Validation: eight store methods and six receiver methods pass, including actual authenticated loopback TLS submit/read/reply/withdraw, cross-device isolation, fixed retention, withdrawal before upload/restart, actual expiry scheduler and the real local maintenance port. Ten affected release/CLI/TLS lifecycle methods also pass. One initial receiver-test import error (nonexistent LocalPolicy fixture) was corrected to the inert policy object unused by the feedback route; no product exception was hidden. No real issue, supplier inference, APK install or device tests were performed.


## Independent-review correction

Independent QA on original head `40052d52` found that after a withdrawn UUIDv4 tombstone was purged at the original deadline, the same key could create another issue with a fresh seven-day lifetime. That head is blocked and must not be accepted. The correction binds new keys to their original creation time using UUIDv7, checks freshness only for first admission, and allows existing admitted retries without extending retention. Android must generate/persist the new key at the original submit decision and never refresh its timestamp for a retry.

Eleven store + seven receiver methods now pass, including the actual receiver sequence successful submit → withdraw → original deadline → erased rows → same-key replay rejected, store restart, admission boundaries, legacy keys and short-lived unknown-key tombstones. Original scenarios now use legitimate UUIDv7 fixtures; the replay regression first proves initial admission succeeded before asserting expiry rejection. No original retention/withdrawal oracle was weakened. Production clock/device interoperability and the independent re-review remain pending.


A second independent boundary check found that an out-of-window future key was incorrectly acknowledged as already deleted. Advancing one millisecond could make that key admissible. Withdrawal now returns an explicit clock failure for such a key, with no deletion receipt; it never claims DELETED for a request it cannot safely tombstone. Permanently inadmissible expired/legacy keys may still acknowledge an empty store without retaining identifiers. The exact receiver counterexample is retained as a regression. New total: 11 store + 8 receiver methods pass; independent re-review remains required.
