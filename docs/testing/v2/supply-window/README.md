# 两包与四包发送窗口的对照

在仓库根目录运行 `scripts/with-build-lock python3 -B -m unittest tests.v2.test_supply_window`。这只使用临时本机 WebSocket，不使用生产监听器、Mac 诊断 peer 或供应商。测试对同一个两句 PLAN 执行整答和逐句审核，两次合成各输出 24 个 20 ms 的固定 PCM 块。每次拉取模拟供应商耗时 3 ms，第二句也须经过审核并打开自己的资源。播放头按 24 kHz 随单调钟前进；客户端仅在整包播完再经 35 ms 的返回延迟发送 ACK。35 ms 是用于复现回压的条件，不能视为手机实测 RTT。

输出统计区分供应商的受控延时、实际相邻拉取间隔（包含下游回压）、窗口满时 audio 调用的时间、实际 WebSocket 发送间隔、两句 TTS 资源之间的审核等待，以及新资源到首 PCM。strict_loss 仅累计相邻播放游标都在首尾之间时的饥饿帧数，属于模拟播放头指标；真机以同一 active 音轨满足 `0 < previous < current < final_active_cursor` 的 AudioFlinger 样本另算，舍弃跨最终游标区间。模拟与设备不可混算。

`python3 -m backend.v2.live ... --wide-audio-window` 仅扩大待播放确认的 PCM 包上限（2 → 4），不改变单包 2400 帧上限。最大额外在途量为 4800 帧 / 200 ms；这不是打断后的许可播放时间，取消仍须立即撤销和 flush。默认维持两包；回滚移除参数并重启 V2。窗口不能消除长时间无供应商数据或下一句尚未通过审核造成的断供。既不提前确认，也不提前审核或生成下一句。

root 若在 Mac 窗口结束后安排同夹具对照，应保留相同客户端、播放路径、采样频率与三轮输入；按各音轨报告严格区间覆盖数、出现增量的区间数和欠载增量，同时核实最终 ACK 和打断，避免把起播/收尾计作句中停顿。
