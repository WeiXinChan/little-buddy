# 安卓构建、签名与 APK 交付方案

本方案覆盖 V0 互动包和 V1 安卓验收包，依据 [需求](../requirements.md)、[总体设计](design.md)、[开发计划](development-plan.md) 和 [验收方案](acceptance.md)。

文档评审以操作步骤、责任人、放行证据和失败处置齐备为准。下文的工具链冻结、锁与资源验证、密钥恢复演练、分发验证及真机安装均为实施阶段验收项，目前待执行。

## 环境实测与工具链冻结

| 项目 | 2026-11-20 构建服务器实测 |
| --- | --- |
| CPU 和内存 | 4 个逻辑 CPU，3.6 GiB RAM，约 2.5 GiB 可用，1.9 GiB swap |
| 磁盘 | 工作目录所在卷约 40 G，检查时剩余约 25 G |
| JDK 和 Android 工具 | PATH 未找到 `java`、`javac`、`sdkmanager`、`adb`、`gradle`。未设置 `JAVA_HOME`、`ANDROID_HOME`、`ANDROID_SDK_ROOT`，常见安装目录未发现 JDK 或 SDK |
| 仓库 | 基线 `c6549c5` 已含总体设计、开发计划和验收方案 |

首构建前按 AGP 兼容矩阵冻结并在仓库登记 JDK 发行版和完整版本、SDK Command-line Tools、目标平台 API、Build Tools、Gradle Wrapper、AGP、Kotlin/Compose、compileSdk 和 targetSdk。提交 Wrapper 及 `distributionSha256Sum`。在干净环境核对实际解析版本及 Wrapper 发行包校验。设计建议 minSdk 26，首验基线为 OPPO Android 16 / ColorOS 16.0.5，实际机型和系统由用户确认。

## 固定签名与灾难恢复

1. 首包前由用户指定签名保管人和受控签名环境。保管人生成专用 release 密钥，登记别名、证书 SHA-256 指纹和到期日。同一升级线的 V0 和 V1 始终使用相同 `applicationId` 与证书。调试包使用独立应用 ID 和调试签名。
2. 签名保管人将密钥库存于仓库外，仅签名账户可读。对 unsigned APK 先做 ZIP 对齐，在本地受控终端关闭 shell 跟踪和会话录制，设 `umask 077`，在加密存储上的私有临时目录操作。使用 `apksigner sign --ks <密钥库路径> --ks-key-alias <别名> --out <签名APK> <对齐后的APK>`，在工具提示时交互输入密钥库和密钥口令。口令只通过交互提示输入，日志只记录结果及公开指纹。签名成功、失败或中断均清理解密副本与未完成产物，若异常退出则在下次操作前检查并清理残留。签名后对最终 APK 核验签名、证书指纹和 manifest 中的应用 ID、版本与 SDK 约束。
3. 首包前请用户确认备份格式、恢复材料位置和应急授权人。推荐用用户认可的口令加密归档格式，由保管人交互加密，保留两份位于独立故障域的密文，例如两处分别存放的离线介质。备份解密口令与密钥库、密钥条目口令放在与两份副本独立的用户控制位置，例如另处封存的恢复材料。用户保管副本及恢复位置索引。主签名机或日常凭据不可用时，由用户本人取用，或授权预先指定的恢复人从独立位置分别取得加密副本和所需口令。登记格式、责任人、取用路径和演练日期，登记册只保留索引和公开指纹。
4. 首包前用独立测试密钥演练。分别确认两份副本可读，模拟主机失效，从其中一份在干净环境解密，核对预登记证书指纹，签一个一次性测试 APK，再用 `apksigner verify --verbose --print-certs` 验证并清理。检查 Git 变更、构建与签名日志、缓存、临时目录和解包后的 APK，确认签名秘密及后端服务密钥均未进入交付链。正式密钥归档后按同一路径核对两份备份可解密并与登记指纹一致，再放行首包。
5. 密钥丢失、疑似泄露、备份无法恢复或指纹不符时，暂停签名和发包。保管人从可信副本恢复并核验。无法恢复或怀疑原密钥泄露时，由用户另行决定迁移和设备兼容性方案。涉及卸载或重装先核对本地数据影响并取得用户同意。

## 版本、主机锁与资源预算

- 建议 V0 首包 `versionName=0.1.0`，V1 首包 `versionName=1.0.0`。由唯一发布登记人分配同一升级线上严格递增的整数 `versionCode`，已分配的编号即使撤回也不复用。文件名为 `little-buddy-<versionName>-<versionCode>.apk`。登记应用 ID、Git SHA、构建配置、兼容范围和已知限制。
- 实施前由服务器管理员一次性创建唯一锁 `/var/lock/little-buddy/heavy.lock`，目录和普通文件都由 root 所有，目录 `0755`、文件 `0644`。若 `/var/lock` 指向易失目录，开机时由管理员管理的 tmpfiles 规则恢复。构建账户通过只读文件描述符对该路径执行 `flock -n`。入口固定此路径，拒绝缺失、软链接或权限异常的锁，checkout 无权创建、替换、删除锁或覆盖路径。构建、工具链大批下载与安装、重型压测经同一入口，锁忙即退出并报告占用。锁覆盖资源检查、实际任务和子进程退出，运行期间管理员也不替换锁文件。
- 取得锁后再用 `free -h` 和 `df -h` 检查可用内存和 SDK、Gradle 缓存、临时目录、产物与日志所在卷。同卷合计预计写入量。首次工具链和缓存预估 10–12 GiB，产物和日志约 2 GiB。每个受影响卷预计写入后至少留 8 GiB，启动前主机可用内存至少 2.5 GiB。未达门槛先释放资源或重新安排，重新取得锁并检查。
- 首构建推荐 Gradle `--no-daemon --max-workers=2`、Gradle JVM 堆上限 1 GiB、设置 `kotlin.compiler.execution.strategy=in-process` 将 Kotlin 编译计入 Gradle 堆，测试任务设置 `maxHeapSize=256m` 和 `maxParallelForks=1`。使用独立的 systemd 临时服务，在 cgroup v2 对整棵任务进程设置 `MemoryMax=2G`、`MemorySwapMax=0`，并设置 `OOMPolicy=kill`，覆盖 JVM 非堆、编译工具、测试及其子进程。入口前台等待该服务和整个 cgroup 退出后才释放锁，取消或失败时停止该服务并确认子进程已退出。首构建前用轻量任务验证限制实际生效及退出清理，系统无法应用限制时先解决运行环境。默认关闭模拟器。
- 按 A6 记录冷构建 cgroup 总内存峰值、各卷磁盘低水位、耗时和结果。构建中监测剩余磁盘，逼近 8 GiB 时停止并检查写入量。遇到 OOM、磁盘不足或预算超限，保留脱敏资源记录与错误码，丢弃不完整产物，清理后结合峰值调整并发或分批执行，再重新检查并重跑。首构建前从两个 checkout 用轻量任务验证持锁期间第二个入口拒绝运行，释放后可重新取得锁。

## APK 分发与 Mac 安装

1. **首包前验证分发。** 默认候选是受限工单附件。用不含敏感信息、文件类型为 APK、大小覆盖预计首包的测试包试传，记录已知平台上限或实测可用尺寸及失败信息。由实际接收用户登录下载并核对 SHA-256。同时用未授权账号和退出登录的隔离浏览器，验证工单与复制转发的下载链接均拒绝访问。签名 URL 也按转发场景实测。对记录只保留大小、哈希、权限结果和错误码。
2. 上传超限、用户下载失败或权限过宽时，暂停该渠道，若样件已暴露则移除附件或撤销链接。请用户在首包前确认是否有可按账号授权的备用渠道，若有，在该渠道重复同尺寸上传、目标用户下载、未授权与匿名访问、哈希校验。所有候选均失败或没有已确认的私有渠道时暂停发包，由用户确认后续渠道。文档评审阶段无需配置渠道。
3. **实际发包。** 对最终签名 APK 运行 `apksigner verify --verbose --print-certs <APK>`，确认登记指纹后在产物目录运行 `sha256sum "$apk_name" > SHA256SUMS`，其中 `apk_name` 为最终 APK 文件名。在通过验证的受限渠道提供 APK、校验文件和发布说明，记录 APK 与证书的 SHA-256、版本/提交、安装条件、测试和限制。发布人重下载核对字节哈希。实际包超过已验证大小或下载方式、权限发生变化时，重新验证分发。
4. **Mac 校验与安装。** 在个人 Mac 进入下载目录，运行 `shasum -a 256 -c SHA256SUMS`，并与工单发布记录核对。可用 Android SDK Build Tools 的 `apksigner` 另验签名和证书指纹。哈希或指纹不符时暂停安装，核对受限工单记录并重新取包。首包时用正确样本和改动一字节的副本验证校验流程。
5. 从 Android 官方渠道取得 Platform Tools。在 OPPO 开启开发者选项和 USB 调试，连接数据线并确认 Mac 调试授权。`adb devices` 应显示目标为 `device`，多设备用 `adb -s <serial>`。首次安装运行 `adb install 文件名.apk`，同签名升级运行 `adb install -r 文件名.apk`。用 `adb shell dumpsys package <applicationId>` 核对版本。首包阶段用同证书、不同编号的两包验证首装和覆盖升级，升级前先记录一项可观察的本地状态，升级后确认保留且能启动。签名冲突或版本降级时保留原安装，核对包、指纹和编号。验证结束可关闭 USB 调试。
